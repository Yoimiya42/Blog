# 个人网站 · 架构与工程规范

> 版本 v0.1 · 2026-08-29
> 本文档回答两个问题：**怎么设计才能以后加功能不用推翻重来**，以及**怎么把这个项目做成一次完整的软件工程实践**。
> 需求见 `01-requirements.md`，重大决策记录见 `adr/`。

---

## 1. 扩展性的设计思路

### 1.1 先说清楚：扩展性不等于「什么都做成插件」

新手最容易犯的错，是为了「以后可能用得上」而把所有东西都抽象一遍。结果是代码绕来绕去、改一个小功能要跳七八个文件、而那些预留的扩展点九成永远用不上。这叫**过度设计**，它比不做扩展性更伤项目。

正确的做法是**找准变化点**：分析清楚哪些地方将来大概率会变，只在那几个地方留口子；其余地方怎么直白怎么写。

对本项目做的变化点分析：

| 大概率会变（要留口子） | 大概率不变（直接写） |
|---|---|
| 新增内容类型（除了影书游行，以后可能有播客、展览、专辑、健身记录…） | 用户和会话模型 |
| 新增互动方式（点赞、收藏、投票…） | 图片资产的存储与引用方式 |
| 新增内容元数据的外部数据源（TMDB 之外的） | Markdown 的渲染管线 |
| 换图床、换邮件服务、换数据库托管商 | 路由与页面组织方式 |
| 新增登录方式 | 标签系统 |
| 内容发布后要触发的副作用越来越多 | |

下面每一条设计，都是针对上表左栏某一项的。

### 1.2 通用原则

- **三次法则**：同样的东西写第三遍再考虑抽象。写两遍的重复是可以忍受的，过早的抽象不可以。
- **YAGNI**：不要实现「以后可能需要」的功能。但**要预留**「以后可能需要」的位置（加字段比改表结构便宜得多）。
- **依赖倒置**：业务代码依赖「接口」，不依赖「某个具体服务」。换服务时只换实现。
- **配置优于硬编码**：能写进配置文件的，不要散落在代码各处。
- **单一出口**：每个功能模块只通过一个 `index.ts` 对外暴露，内部结构随便改，外部不受影响。

## 2. 分层架构

### 2.1 三层，边界严格

```
路由 / 页面层 (app/)          只做组装：取数据、传给组件、处理跳转
        ↓  只能调用
业务逻辑层 (service)          业务规则、权限判断、事务、触发事件
        ↓  只能调用
数据访问层 (repository)       唯一允许碰数据库的地方
        ↓
        Prisma / PostgreSQL
```

**硬规则（用 ESLint 强制，违反就报错）**：

1. `app/` 目录下**禁止** import `prisma`。页面不能直接查数据库。
2. 只有 `*.repository.ts` 文件可以 import `prisma`。
3. 跨功能模块只能 import 对方的 `index.ts`，**禁止**深入到对方的内部文件。

第 3 条是最重要的一条。它保证了「模块内部怎么改都不会波及别人」，这是扩展性的地基。ESLint 的 `no-restricted-imports` 规则可以直接把这条变成编译期报错，不靠自觉。

为什么这么做：三个月后你想重构文章模块的数据结构。如果别的模块直接引用了文章模块的内部文件，你得把整个项目翻一遍；如果所有人都只用 `index.ts`，你只要保证出口签名不变，内部随便拆。

### 2.2 目录结构

```
src/
  app/                        # Next.js 路由，只做组装
    (site)/                   # 公开站点分组
      page.tsx                #   个人主页
      blog/[slug]/page.tsx
      moments/page.tsx
      life/[type]/page.tsx
      gallery/page.tsx
    (admin)/admin/            # 管理后台分组，独立 layout
    api/                      # 接口路由
  features/                   # ★ 按业务功能切分，每个自包含
    post/
      components/             #   该功能专属 UI
      server/
        post.service.ts       #   业务逻辑
        post.repository.ts    #   数据访问（唯一碰 prisma 的地方）
      schema.ts               #   zod 校验规则 + 推导出的类型
      index.ts                #   ★ 对外唯一出口
    moment/  item/  photo/  comment/  auth/  media/  tag/
  components/
    ui/                       # 无业务的通用组件（Button、Input…）
    layout/                   # 页头页脚导航
  lib/                        # 跨功能的基础设施
    db.ts                     #   Prisma 客户端单例
    storage/                  #   ★ 存储适配器（接口 + R2 实现）
    mail/                     #   ★ 邮件适配器（接口 + Resend 实现）
    metadata/                 #   ★ 外部元数据适配器（TMDB / IGDB / OpenLibrary）
    events.ts                 #   ★ 事件总线
    auth.ts
    env.ts                    #   环境变量集中校验
  config/                     # ★ 配置驱动的扩展点
    content-types.ts          #   内容类型注册表
    site.ts                   #   站点信息
    navigation.ts             #   导航结构
  styles/
prisma/
  schema.prisma
  migrations/                 # 每次结构变更一个文件，永不手改线上库
  seed.ts                     # 开发用的测试数据
docs/
  01-requirements.md
  02-architecture.md
  adr/                        # 架构决策记录
tests/
  unit/  e2e/
```

带 ★ 的五处，就是本项目全部的扩展点。其余地方直白地写就好。

## 3. 五个扩展点的具体设计

### 3.1 内容类型注册表（`config/content-types.ts`）

**要解决的问题**：以后你想加「播客」「看过的展览」「听过的专辑」，不希望复制粘贴一遍电影模块。

```ts
export const contentTypes = {
  movie: {
    key: 'movie',
    label: '电影',
    labelEn: 'Films',
    route: '/life/movies',
    icon: FilmIcon,
    coverAspect: '2/3',              // 海报是竖的
    metadataProvider: 'tmdb',        // 用哪个数据源抓封面
    extraFields: ['director', 'runtime', 'country'],
    features: { rating: true, review: true, visitorRating: true },
  },
  book:  { /* coverAspect: '2/3', provider: 'openlibrary', … */ },
  game:  { /* coverAspect: '3/4', provider: 'igdb',       … */ },
  place: { /* coverAspect: '3/2', provider: null,          … */ },
} satisfies Record<string, ContentTypeConfig>
```

列表页、详情页、后台录入表单全部读这份配置来渲染。**新增一个内容类型 = 在这里加一项**，不改任何已有代码。这是本项目最重要的一个扩展点。

### 3.2 可插拔适配器（`lib/storage`、`lib/mail`、`lib/metadata`）

**要解决的问题**：现在用 Cloudflare R2 存图。万一以后要换成阿里云 OSS（为了大陆速度），不希望满项目搜 `r2` 这个词。

做法是先定义接口，业务代码只认接口：

```ts
// lib/storage/types.ts
export interface StorageAdapter {
  upload(file: Buffer, key: string, mime: string): Promise<{ url: string }>
  delete(key: string): Promise<void>
  getSignedUrl(key: string, ttl: number): Promise<string>
}

// lib/storage/r2.ts        -> class R2Storage implements StorageAdapter
// lib/storage/index.ts     -> export const storage: StorageAdapter = new R2Storage()
```

换服务时只改 `index.ts` 一行。邮件、外部元数据源同理。元数据源尤其明显：加一个 `SpotifyProvider` 就能支持专辑，其它代码一行不动。

这就是软件工程课里的**依赖倒置原则**，在这个项目里你能真切感受到它省了什么。

### 3.3 多态互动（评论 / 点赞 / 收藏）

**要解决的问题**：现在只有评论。以后想加点赞、收藏、投票，不希望每种内容各写一遍。

评论表已经用 `targetType` + `targetId` 设计（见需求文档第 5 节）。同一套模式可以复用给未来的 `Reaction` 表。新增一种可被评论的内容 = 在 `CommentTarget` 枚举里加一个值 + 在注册表里声明 `features.comment: true`，评论组件本身不改。

代价要说清楚：多态设计**没法用数据库外键约束**，数据一致性要靠应用层保证（删除文章时要记得删它的评论）。这是个真实的取舍，写进 ADR 里。

### 3.4 事件总线（`lib/events.ts`）

**要解决的问题**：发布一篇文章时要做的事会越来越多——生成分享用的 OG 图片、通知订阅者、更新站点地图、清 CDN 缓存、同步到 RSS。如果全部硬写在 `publishPost()` 里，这个函数会越来越长，每加一件事都要改它。

改成发一个事件，谁关心谁自己订阅：

```ts
// 发布时只做一件事
await events.emit('post.published', { postId })

// 各监听器独立注册，互不知情
events.on('post.published', generateOgImage)
events.on('post.published', notifySubscribers)
events.on('post.published', revalidateSitemap)
```

新增一个副作用 = 加一个监听器，`publishPost` 永远不用改。

一个人的项目不需要上消息队列，一个几十行的内存事件总线就够了。等真的需要可靠投递（比如发邮件失败要重试）时，再把它换成队列，接口不变。

### 3.5 数据库演进纪律

数据库是**最难改**的一层，纪律最重要。

- **所有结构变更走 migration 文件**（`prisma migrate`），绝不手动改线上库。migration 文件进 Git，是数据库的版本历史。
- **加字段优先可空或带默认值**，这样旧代码还能跑，属于向后兼容变更。
- **不直接删字段或改名**。要改，走业界标准的三步走「扩展 → 迁移 → 收缩」：先加新字段（两个字段并存）、再把数据搬过去并让代码改用新字段、确认无误后过一两个版本再删旧字段。这个流程叫 expand-migrate-contract，是所有需要零停机的团队的标准做法，值得亲手做一次。
- **每张表都有 `createdAt` / `updatedAt`**。删除用 `deletedAt` 软删除，不要真删——真删的数据找不回来。
- **索引跟着实际查询加**，不要提前瞎加（索引会拖慢写入）。上线后看慢查询再补。
- **JSON 字段是逃生舱，不是万能药**。类型特有字段放 JSON 可以，但凡是需要筛选、排序、聚合的字段，必须是正经的列。
- Neon 是 serverless 数据库，注意冷启动和连接数限制，Prisma 要配连接池。

### 3.6 扩展性的量化验收标准

抽象的原则不好检验，所以定成可测量的目标。项目做完后，下面每一条都应该成立：

| 场景 | 目标 |
|---|---|
| 新增一个清单内容类型（如「展览」） | 只改 `config/content-types.ts`，可选加一个 metadata provider |
| 新增一种可评论的内容 | 加一个 enum 值 + 一行配置 |
| 新增一个登录方式 | 只改 `lib/auth.ts` 一处 |
| 更换图床 / 邮件服务 | 只改对应 adapter 的 `index.ts` |
| 内容发布后新增一个副作用 | 加一个事件监听器 |
| 新增一个静态页面 | 不改任何已有文件 |
| 给某类内容加一个字段 | 一个 migration + schema + 表单，不影响其它模块 |

做到后期可以拿这张表自查。做不到的那几条，就是架构没设计好的地方。

## 4. 软件工程全流程实践

这一节把项目当成一次完整的 SDLC（软件开发生命周期）演练。每个阶段列出业界做法、本项目怎么落、以及你能学到什么。

### 4.1 需求工程（已完成第一轮）

**业界做法**：需求文档、用户故事、验收标准、优先级排序（MoSCoW / RICE）、需求变更流程。
**本项目**：`01-requirements.md`，功能带 FR 编号和验收标准，按 v1 / v1.5 / v2 分级。
**规矩**：任何新想法先加进需求文档并标版本，不直接写进代码。需求变更要在文档末尾的变更记录里留痕。
**你会学到**：为什么「先写清楚再动手」能省时间，以及如何抵抗「想到什么做什么」的冲动——这是新手和工程师最大的区别之一。

### 4.2 架构设计与决策记录

**业界做法**：架构图（C4 模型四层：系统上下文 / 容器 / 组件 / 代码）、ADR（Architecture Decision Record）。
**本项目**：本文档 + `docs/adr/` 目录。
**ADR 是什么**：每做一个重要技术决策，写一页纸，记录「背景是什么、有哪些选项、各自的取舍、最终选了什么、会带来什么后果」。格式固定，编号递增，**只增不改**——决策被推翻时不是去改旧文件，而是写一份新的把旧的标为「已取代」。
**为什么值得做**：半年后你会忘记当初为什么这么选。更重要的是，写 ADR 会强迫你把「我觉得这样比较好」变成「我对比了三个方案，因为 X 所以选 B，代价是 Y」。这个思维训练比任何一行代码都值钱，也是面试时最能体现水平的东西。
**你会学到**：技术选型的方法论，以及如何为决策负责。

### 4.3 项目管理与任务拆分

**业界做法**：Issue 跟踪、看板（To Do / In Progress / Review / Done）、里程碑、Sprint。
**本项目**：GitHub Issues + GitHub Projects 看板，里程碑对应 v1 / v1.5 / v2。
**规矩**：每个功能开一个 Issue，关联 FR 编号；**一个任务的粒度控制在半天内能做完**，做不完说明拆得不够细；每个 commit 和 PR 关联 Issue 号。
**你会学到**：如何把一个大目标拆成可执行、可验收的小块——这是工程能力里最被低估的一项。

### 4.4 版本控制与协作流程

**业界做法**：分支策略（GitHub Flow / Trunk-Based）、Conventional Commits、Pull Request、Code Review。
**本项目**：
- `main` 为唯一长期分支（当前叫 `init`，**建议尽早改名为 `main`**），永远保持可部署。
- 功能开发走短命分支：`feat/blog-editor`、`fix/image-upload`，做完开 PR 合回 `main`。
- Commit 信息用 Conventional Commits：`feat(blog): add tag filtering`、`fix(admin): keyboard covering editor`、`docs:`、`refactor:`、`chore:`。这个格式能自动生成 CHANGELOG。
- **即使只有你一个人，也要走 PR**。开 PR 后自己把 diff 从头看一遍，你会发现大量随手写下的问题。这是零成本的最高性价比实践。
- PR 自审清单（放进 PR 模板）：有没有硬编码？有没有漏掉错误处理？输入校验做了吗？会不会有 N+1 查询？手机上试过吗？
**你会学到**：Git 的正确用法（远不止 add commit push）、代码审查视角、以及如何写出别人（和三个月后的自己）看得懂的提交历史。

### 4.5 测试

**业界做法**：测试金字塔——大量单元测试、适量集成测试、少量端到端测试。
**本项目**：
- 单元测试用 **Vitest**，重点覆盖：业务逻辑（service 层）、工具函数、zod 校验规则、权限判断。UI 组件不必强求覆盖率。
- 端到端测试用 **Playwright**，只写关键路径的冒烟测试：能打开首页、能登录后台、能发一篇文章、能看到它。数量控制在 10 条以内，多了维护成本高。
- 数据库测试用独立的测试库 + `prisma/seed.ts` 造数据。
**节奏**：v1 只给「权限判断」和「输入校验」写单测（这两处出错后果最严重）。v1.5 补关键业务逻辑单测和 E2E 冒烟。不追求覆盖率数字。
**你会学到**：什么样的代码是「可测试的」（提示：分层做对了，测试自然好写；分层做错了，测试根本没法写——测试是架构质量的照妖镜）。

### 4.6 CI/CD

**业界做法**：提交即检查、自动构建、预览环境、生产部署门禁。
**本项目**：
- **GitHub Actions**：每次 push 和 PR 自动跑 `lint` → `typecheck` → `test` → `build`。任何一步失败就不允许合并。
- **Vercel Preview**：每个 PR 自动部署一个独立的预览网址，可以在手机上直接打开验收。这个功能对你尤其有用——改完手机上点开就能看。
- **生产部署**：合并到 `main` 自动部署。
- **本地门禁**：Husky + lint-staged，提交前自动格式化并检查暂存的文件，把问题挡在提交之前。
**你会学到**：自动化的价值，以及「让机器去做重复的检查」这个工程思维。

### 4.7 数据库运维

**业界做法**：迁移管理、种子数据、备份恢复、索引优化、慢查询分析。
**本项目**：
- 迁移全部走 `prisma migrate`，migration 文件进 Git。
- `prisma/seed.ts` 一条命令灌满测试数据，新环境三分钟可用。
- Neon 自带时间点恢复，但**要亲手演练一次恢复流程**——没演练过的备份等于没有备份。
- 上线后定期看慢查询，学会用 `EXPLAIN` 看执行计划，识别 N+1 问题（这是 ORM 最经典的坑，你一定会遇到）。
**你会学到**：数据库不只是「存数据的地方」，它是整个系统里最需要谨慎对待的部分。

### 4.8 可观测性

**业界做法**：错误追踪、结构化日志、性能监控、可用性监控、告警。
**本项目**：
- **Sentry**（免费额度够用）：前后端错误自动上报，出错时你能看到完整堆栈和用户操作路径。接入只要几分钟，回报极高。
- 结构化日志：关键操作（登录、发布、上传、删除）打日志，格式统一便于检索。
- **Vercel Analytics** 看性能，**Umami** 看访问量。
- **UptimeRobot** 免费监控可用性，网站挂了发邮件给你。
**你会学到**：「上线不是结束」。生产环境的问题和本地完全不同，学会观察线上系统是工程师和学生的分水岭。

### 4.9 安全

**业界做法**：对照 OWASP Top 10 逐项自查、依赖漏洞扫描、最小权限原则。
**本项目**：在 v1.5 完成后，拿 OWASP Top 10 清单逐条对着自己的代码检查一遍，写一份自查报告放进 `docs/`。开 GitHub Dependabot 自动检测依赖漏洞。
**你会学到**：安全不是「加个 HTTPS」，而是一套系统性的检查方法。这份自查报告本身就是一个很好的作品集材料。

### 4.10 维护与演进

**业界做法**：依赖更新、技术债登记、重构、版本发布与 CHANGELOG、废弃流程。
**本项目**：
- **技术债台账**：`docs/tech-debt.md`，写代码时遇到「先这样凑合一下」，立刻记一条（位置、问题、影响、建议何时还）。不记就会忘，忘了就变成永久的坑。
- **CHANGELOG.md**：每次发布记录变更，用 Conventional Commits 可以半自动生成。
- **依赖更新**：Renovate 或 Dependabot 自动开 PR，每月处理一次，不要攒到半年后一次性升级（那会是灾难）。
- **定期重构**：每完成一个版本，花半天回头看有没有重复代码、有没有该抽象的地方（三次法则）。
**你会学到**：软件的成本大头在维护而不是开发，这是学校里几乎学不到、工作后天天面对的现实。

## 5. 工程实践的引入节奏

全部一次上会拖垮 v1。按「成本 / 回报」排优先级。

### v1 就要有（便宜且回报高，不做后面补代价大）

TypeScript strict 模式 · ESLint + Prettier + Husky · 分层目录结构与 import 边界规则 · Prisma migration 纪律 · zod 输入校验 · 环境变量集中校验（`lib/env.ts`）· Git 分支策略 + Conventional Commits + 自审 PR · ADR · GitHub Actions 基础检查 · Vercel Preview · Sentry · 权限与校验的单元测试 · 技术债台账

### v1.5 再上

关键业务逻辑单元测试 · Playwright E2E 冒烟 · GitHub Projects 看板正式使用 · Dependabot · 结构化日志 · CHANGELOG 自动生成

### v2 再上

较完整的测试覆盖 · 性能预算与 Lighthouse CI · OWASP 自查报告 · 独立 staging 环境 · 数据库备份恢复演练

### 永远不上（对单人项目是负担，且学不到对的东西）

微服务 · Kubernetes · 自建 CI 服务器 · monorepo · GraphQL（除非专门为了学它）· 事件溯源 · 微前端

判断标准很简单：这些技术解决的是「多团队协作」和「超大规模」的问题。你一个人做一个个人网站，引入它们只会得到复杂度，得不到它们本该带来的收益，而且会让你对这些技术产生错误的直觉。

## 6. 建议的学习顺序

如果目标包含「学会全流程」，那么做的顺序应该和纯粹追求快速上线不同。建议：

1. **先把工程基建搭好再写业务代码**。空项目状态下配好 TS、ESLint、目录结构、CI、部署流水线，先让一个「Hello World」经过完整的 PR → CI → Preview → 生产 流程上线。这一步看似什么功能都没做，但它把整条链路跑通了，后面每个功能都在这条流水线上走。
2. **第一个功能选技术博客，慢慢做，做规范**。它结构最简单，适合把分层、校验、测试、迁移这些实践第一次做扎实。第一个功能做对了，后面都是复制这个模式。
3. **第二个功能（管理后台）开始提速**。模式已经熟了，重点转向解决真实难题（移动端编辑体验、图片处理）。
4. **上线后强制自己维护一个月**。看监控、修 bug、处理线上问题、写 CHANGELOG。这一个月学到的东西可能比前面三个月还多。
5. **然后再做扩展模块**（碎碎念、清单、画廊）。这时才是真正检验扩展性设计的时候——如果加新模块时发现处处要改老代码，回头看第 3 节哪里没设计好。
