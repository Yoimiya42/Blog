# 0001. 采用全栈自建而非静态站点

- **状态**：已接受
- **日期**：2026-08-29
- **相关需求**：FR-ADMIN-*、FR-AUTH-*、FR-SOCIAL-*

## 背景

个人网站有两个需求超出了普通静态博客的范围：一是要能在手机上编辑并发布内容（在外面、只带手机的场景）；二是要有访客账号系统，登录后可以评论、给清单条目打分、给站主发私信。

同时项目的目标之一是学习业界全流程开发，包括数据库设计与运维。

约束：预算每年 30 英镑以内；开发者是前端与后端经验都很少的在校生；第一版希望一个月内上线。

## 考虑过的选项

### 选项 A：静态站点生成（Astro / Next.js SSG）+ Git 存内容
优点：最快、最便宜、几乎零运维；部署到 CDN 性能极佳；内容有 Git 版本历史。
缺点：手机端编辑体验差（需通过 GitHub 网页或第三方 App，传图尤其痛苦）；发布要等构建；用户系统和互动功能完全无法实现，必须另外搭一套后端，等于两套系统。

### 选项 B：静态站 + Git-based CMS（Keystatic / Decap）
优点：保留静态站全部优点；提供网页后台，手机浏览器可编辑并自动提交。
缺点：发布仍有构建延迟；图片上传体验受限；**用户系统依然无解**，仍需额外后端；相当于为了绕开后端而引入了额外复杂度，最后还是要写后端。

### 选项 C：第三方 CMS（Notion 等）作为内容源
优点：手机编辑体验最好（用成熟 App）；开发量最小；Notion 数据库天然适合做清单。
缺点：内容被绑定在第三方平台；图片链接会过期需额外处理；样式与结构受限；用户系统依然无解；且学不到后端与数据库（与学习目标直接冲突）。

### 选项 D：全栈自建（Next.js + PostgreSQL + 自建后台）
优点：手机后台即时发布，体验完全可控；用户系统、评论、评分、私信复用同一套后端，边际成本最低；覆盖前端、后端、数据库、认证、部署、运维的完整链路，与学习目标高度一致；简历价值最高。
缺点：开发量最大；需要学习数据库、ORM、认证、文件上传、权限等多个新领域；有持续的运维责任；第一版周期会更长。

## 决定

选择 **选项 D：全栈自建**。

两个理由。第一，用户系统是硬需求，而任何静态方案都绕不过它——绕开后端只是把成本推迟，最终还是要付，而且会付两次。既然后端必然要写，让它同时承担内容管理，边际成本反而最低。第二，项目目标明确包含学习完整的软件工程流程与数据库实践，选项 A、B、C 都会把这部分学习内容排除在外。

技术栈：Next.js 15（App Router）+ TypeScript + PostgreSQL（Neon）+ Prisma + Auth.js + Cloudflare R2 + Vercel。

## 后果

**好的**：一套后端服务所有需求；发布即时生效；扩展新功能（点赞、收藏、订阅）时基础设施已就位；覆盖完整技术链路。

**坏的 / 需要承担的代价**：v1 周期比静态方案长约两到三周；需要承担数据库运维、备份、安全、GDPR 合规责任；有了用户数据就有了持续的责任，不能随便废弃；需要处理垃圾评论与内容审核。

**以后如果要改**：从全栈退回静态很容易（导出内容为 Markdown 即可）；反方向则很难。所以这个决定是「先难后易」的方向，风险可控。
